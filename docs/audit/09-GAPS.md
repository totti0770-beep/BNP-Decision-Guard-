# 09 — Gaps

What this audit has **not** established, stated as plainly as what it has.

## Coverage, as the shell reports it

`docs/audit/_VERIFICATION.txt` is the raw output of the prescribed Phase 3
block, run on this commit. At the time of writing:

```
ON DISK : 230
READ    : 58
MISSING : 172
```

**The file-by-file audit is 58 of 230 — it is not finished.** Any statement in
these reports about a file in `_NOT_READ.txt` would be unsupported, and there
are none: the reports cite only files that have been opened, and the executive
summary's counts come from commands (`grep`, `find`, a route-classifying script)
rather than from reading.

That distinction is the point of keeping the ledger. A counted fact — 50 routes,
18 web pages, 0 TODO markers, 15 entities — is produced by a command over the
whole tree and is as true at 58 files read as at 230. A described fact — what a
service does, why a comment says what it says — requires the file to have been
opened, and only 58 have.

## ⚠️ UNVERIFIED ASSUMPTIONS

These are not claims. They are things a reader might assume from the reports
that this audit did **not** prove.

1. **That the production corpus is what anyone thinks it is.** Production
   reports roughly 2,706 chunks. I have never seen those documents, their
   titles, their sources, or their approval history. `GET /documents/inventory`
   answers this and has not been run against production. Nothing in any report
   here describes the real corpus.
2. **That the live deployment matches this commit.** `infra/railway/README.md`
   documents auto-deploy from `main`; I have not queried the running service to
   confirm which commit it serves, and this branch is not merged.
3. **That `quay.io/minio/minio` is a durable answer.** It resolved in CI on
   `a46181d` — the stack came up and Playwright ran, which is real evidence —
   but this sandbox cannot reach quay.io, and one green run is not a guarantee
   about a registry outside the project's control.
4. **That the web UI behaves correctly.** There are **no web unit tests**. The
   browser smoke exercises a documented flow; everything else about the web app
   rests on it compiling and on manual use.
5. **That the mobile screens work.** `apps/mobile` has 32 unit tests, all of
   them over `src/api.ts` and `src/i18n.ts`. No screen has runtime coverage.
6. **That the answers are clinically sound.** Nothing automated can establish
   this, and nothing here attempts to. See `docs/clinical-validation.md` §6.
7. **That `staleRetrievable` is zero in production.** The startup check logs it;
   I have not read a production log.

## Open questions for a developer or operator

1. Where did the 2,706 production chunks come from, and were those documents
   approved through the governed workflow?
2. Which commit is the Railway deployment currently serving?
3. Is `EMBEDDING_PROVIDER` on production `openai`, and does the stored corpus
   match it? A mismatch makes the assistant refuse everything — safe, but
   silent to a nurse.
4. Does the hospital have an MRN format? `PHI_MRN_PATTERN` is shipped disabled
   and one variable away from being enforced.
5. Who is the qualified reviewer, and when can they sit down with the sheet?
